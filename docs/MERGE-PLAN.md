## 2. 모의 병합: 쌓인 순서대로 합치면 충돌이 나는가

main에서 시작해 #1 → #2 → #3 → #4 → #5 → #6 → #9 → #11 → #12 순서로, 각 PR 머리를 병합 커밋으로 합치는 과정을 `git merge-tree --write-tree`와 `git commit-tree`로 계산했다(참조는 만들지 않음).

- 계산에서 #1은 빨리 감기로 들어간다(GitHub에서 '병합 커밋' 방식으로 합치면 #1에도 병합 커밋이 생기며 트리는 같다). 나머지 여덟 번은 병합 커밋이 필요하고, 글자 충돌은 모두 0이다.
- 마지막 결과 트리 `87aadf2`는 작업 줄기 `9674275`의 트리와 같다.

어느 길로 가든 main의 최종 코드는 같다는 뜻이다. 길에 따라 달라지는 것은 GitHub 기록, 중간 상태, 작업량이다. 이 계산은 `9674275` 기준이고 글자 충돌만 본다. 실제로 올릴 커밋이 바뀌면 다시 계산한다. 중간 상태(예: #3까지 합친 main, 즉 v2 셸 + #2의 `42cecaa` + #1)는 어떤 브랜치에서도 검사한 적 없는 조합이다.

## 3. 선택지

### 가. 작업 줄기를 한 번에 올린다(PR #12를 main 기준으로)
작업 줄기를 원격에 올린 뒤 PR #12의 기준을 main으로 바꾸고(`gh pr edit 12 --base main`), 본문을 새로 써서 '병합 커밋'으로 합친다. #1·#2는 커밋이 main에 들어가므로 GitHub가 '병합됨'으로 표시한다. PR 커밋이 직접 push나 다른 PR로 기준 브랜치에 들어가도 병합됨으로 표시한다는 것이 GitHub 동작이다([GitHub 변경 기록 2023-09-26](https://github.blog/changelog/2023-09-26-more-details-provided-when-a-pull-request-is-merged-indirectly-or-is-still-processing-updates/)). #3·#4·#5·#6·#9·#11 여섯 개는 기준이 중간 브랜치라 자동으로 바뀌지 않으므로 "PR #12로 main에 포함됨" 코멘트와 함께 닫는다.

- 장점: main에 올라가는 상태가 작업 줄기 그대로다. 병합 직전에 검사한 커밋과 main이 정확히 같다. 병합은 한 번이고 충돌은 없다. main이 가리키는 상태(1차 부모 기준)가 검사하지 않은 조합을 거치지 않는다. 작업 줄기 안의 개별 커밋은 원래대로 이력에 들어간다. 병합 커밋 하나가 경계가 되므로, 필요하면 `git revert -m 1 <병합 커밋>` 한 번으로 통째로 되돌릴 수 있다.
- 단점: PR #12의 비교 화면이 213파일·44만 줄이 되어 GitHub에서 줄 단위 검토는 사실상 못 한다. 나로 가도 #12 하나가 182파일 +420,779줄이라 이 부담은 거의 줄지 않는다. 다만 지금까지 검토는 PR 단위가 아니라 작업 단위의 독립 검토(opus-reviewer)로 해 왔고, GitHub 리뷰 기록은 어느 PR에도 없다. 그 여섯 PR은 '병합됨'이 아니라 '닫힘'으로 남는다(커밋은 main에 들어 있다). PR #12 제목·본문을 전체 내용에 맞게 다시 써야 한다.
- 변형: GitHub 병합 대신 작업 줄기를 main에 빨리 감기로 push할 수도 있다. 병합 커밋 없이 이력이 작업 줄기와 같아지지만, 되돌릴 경계가 없고 PR #12는 기준을 먼저 main으로 바꿔 두어야 '병합됨'으로 남는다. 병합 커밋 방식을 권한다.

### 나. 쌓인 순서대로 합친다(#1 → #2 → #3 … → #12)
#1·#2를 main에 합치고, #3부터는 기준을 main으로 바꿔 차례로 합친다. 병합한 PR의 머리 브랜치를 지우면 그 브랜치를 기준으로 하던 다음 PR의 기준이 자동으로 main으로 바뀐다([GitHub 문서: 브랜치 만들기와 지우기](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/proposing-changes-to-your-work-with-pull-requests/creating-and-deleting-branches-within-your-repository)). 브랜치를 지우지 않으려면 `gh pr edit <번호> --base main`으로 하나씩 바꾼다.

- 장점: 모든 PR이 '병합됨'으로 남고, main 이력에 PR마다 경계가 생긴다.
- 단점: 병합 9번(GitHub 병합 커밋 방식이면 #1도 병합 커밋)과 기준 변경 7번(#3·#4·#5·#6·#9·#11·#12)이 필요하다. 중간 상태 여덟 개가 main 이력에 남는데, #1만 합친 상태(= #1 머리)를 빼면 어느 브랜치에서도 검사한 적 없는 조합이다. 도중에 멈추면 main이 검사 안 된 상태로 남는다. 저장소가 squash·rebase도 허용하므로 한 번이라도 잘못 고르면 다음 PR의 커밋이 main의 조상이 아니게 되어, 같은 변경이 두 번 들어오며 충돌이 생긴다. #11 본문('경제 층(작업 중)')처럼 낡은 본문이 그대로 병합 기록이 되고, #12는 #1~#11을 합친 뒤에도 220커밋(246 − 26)짜리라 본문을 다시 써야 하는 일은 가와 같다. 열린 PR의 머리 브랜치를 먼저 지우면 그 PR은 병합되지 않고 닫히므로 순서를 지켜야 한다(같은 GitHub 문서).

### 다. squash 한 커밋으로 올린다(권하지 않음)
커밋 246개의 이력과 병합 기록이 한 커밋으로 사라진다. #1~#11(#10 제외)의 머리 커밋이 main의 조상이 되지 않아 자동 '병합됨' 표시도 없다. 무엇보다 지금 진행 중인 `lane/*` 브랜치들이 main과 조상 관계를 잃어, 다음에 main으로 합칠 때 같은 변경이 겹쳐 충돌한다.

## 4. 추천

**가**를 권한다. 근거는 세 가지다. 최종 코드는 두 길이 같으므로(§2) 고를 기준은 검증된 상태와 작업 위험인데, 가는 main이 곧 검사한 커밋이고 main이 거치는 중간 상태가 없다. PR 경계를 남기는 나의 이점은, 리뷰 기록이 비어 있고 검토를 작업 단위로 해 온 이 저장소에서는 작다. 병합 한 번과 닫기 여섯 번이 병합 아홉 번·기준 변경 일곱 번보다 실수할 곳이 적다.

나를 고를 이유가 있다면, 사용자가 PR 목록에서 모든 PR이 '병합됨'으로 보이기를 원하거나 main 이력에서 시안 단계(#3~#6)를 따로 되돌릴 일이 있다고 보는 경우다.

시점은 2022 짝 완성 판정까지 기다릴 필요가 없다고 본다. main을 쓰는 배포가 없고 main 자체가 바뀌지 않으므로 늦춰서 생기는 충돌 비용은 없다. 반대로 늦출수록 PR #12가 커질 뿐이다. 다만 교실 태블릿용 https 배포를 main 기준 GitHub Pages로 정하면([CLASSROOM-CHECK-LEAGUE](CLASSROOM-CHECK-LEAGUE.md) 준비 1) main이 교실 주소가 되므로, 그때부터는 main 병합 시점을 수업 일정과 함께 정해야 한다. 다만 진행 중인 갈래가 작업 줄기에 들어간 뒤 그 커밋에서 전체 검사를 한 번 통과시키고 올리는 것이 맞다. 작업 줄기 `9674275` 자체의 전체 검사 기록은 저장소 문서와 커밋 본문에서 찾지 못했다. 가장 가까운 기록은 저장소 밖 총괄 인계(`~/Projects/kentech-wt/_briefs/lead-handoff.md`)에 있다. 9674275의 첫 부모 `099f7ac`에서 회귀 15종 0(base·s-riverdeal은 부하 중 1건, 단독 재실행 0), 리그 브라우저 12종 0, Node 전부 0이고, 9674275에서 2022 회귀 5종 0이다. 실행 로그가 저장소에 없어 이 문서에서는 확인하지 못했다. 저장소 안의 기록으로는 AUDIT-2022 §9의 순차 회귀 15종(`lane/2022`의 8b00546·628630c·bbcdfff, 리그 S7·S8 병합 전), S8b 보고의 Node 검사(f07d684, 기준 468a647, 브라우저 미실행), HANDOFF-econ §10의 `cc8fd25` 전체 검사가 있다.
