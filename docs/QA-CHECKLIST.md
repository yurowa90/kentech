# 출시 QA 체크리스트와 판정 규칙

2022 확장판(전력 리그)의 품질과 출시를 사람의 인상이 아니라 체크 결과로 판정한다(D-93). 품질 기준표(`docs/QUALITY-*.md`)의 구간 문장을 하나의 체크 = 하나의 관찰 가능한 조건으로 쪼갰고, 체크 결과에서 항목·축 점수와 출시 판정이 기계적으로 나온다.

## 1. 파일

| 파일 | 내용 |
|---|---|
| `tests/qa/checklist.json` | 원본. 체크마다 ID, 항목, 구간, 무엇을 보는지, 통과 조건, 확인 방법, 다시 돌릴 절차, 이미 있는 검사, 원문 위치 |
| `docs/qa/<축>.md` | 원본에서 만든 읽기용 문서(`ux`, `edu`, `model`, `visual`, `stability`, `common`, `release`). 손으로 고치지 않는다 |
| `tests/qa/render.py` | 원본 → 읽기용 문서. `--check`는 문서가 원본과 같은지만 본다 |
| `tests/qa/score.py` | 판정 결과 파일 → 항목·축 점수, 개발 단계 점수, rc·정식판 판정 |
| `tests/qa/test_score.py` | 점수 규칙 단위 검사 |
| `docs/RECORDING-CRITERIA.md` | 녹화 재확인 판정 기준(체크 CM-REC가 인용) |

체크 수(구간 6·8·10, 제안은 점수 밖): UX 55, 교육 55, 모형 68, 시각 93, 안정성 81, 축 공통 47, 릴리스 관문 131.

## 2. 판정 규칙

**체크 상태**는 통과·실패·확인 못 함·해당 없음 넷이다. 확인 못 함은 통과가 아니다.

**항목 점수**(모든 축 같은 규칙, 구간은 누적):
- 6 구간 체크를 모두 통과하면 6, 6·8을 모두 통과하면 8, 6·8·10을 모두 통과하면 10.
- 아래 구간을 모두 통과하고 위 구간 체크를 절반 넘게 통과하면 그 사이 홀수(5·7·9). 6 구간을 절반 넘게 통과하지 못하면 4.
- 해당 없음은 그 구간 셈에서 뺀다. 제안(proposal) 체크는 셈하지 않는다.

**축 점수**는 항목 점수의 평균에 원문 기준표의 축 규칙을 더한다.
- UX: 휴리스틱 관문(UX-H-01)이 실패하면 8 이상으로 적지 않는다. 한 항목이라도 4 이하면 5 이하.
- 안정성: 가장 낮은 두 항목의 평균을 넘지 않는다.
- 교육·모형·시각: 평균 그대로.

**현장 확인 전**: 확인 방법이 실기기·실연결·교실인 체크가 확인 못 함이면, 그 체크를 뺀 **개발 단계 점수**를 함께 낸다. 예: '8(현장 확인 전)'.

**채점 유효 조건**(실행 전제, 독립 평가자 규칙, 채점 기록 형식, 녹화 판 일치, 무거운 실행 기록 — 공통 체크 가운데 `validity`)은 점수에 넣지 않는다. 하나라도 통과하지 못하면 그 판정은 무효다.

**출시 판정**
- rc 후보(`vX.Y.Z-rc.N` 태그 전): 채점 유효 조건 통과 + rc 단계 릴리스 관문 모두 통과 + 다섯 축의 개발 단계 점수 8 이상 + 마일스톤의 열린 blocker·major 0.
- 정식판: 위에 더해 정식 단계 관문(실기기·실연결·교실 확인 포함)까지 모두 통과 + 다섯 축 점수 8 이상.

## 3. 증거 규칙

- 판정은 평가 SHA 하나에 대해 한다. 녹화 재확인은 녹화 SHA와 평가 SHA의 앱 파일(`ui/ app.js data.js practice-data.js index.html styles.css ext/ games/ g20*.js`)이 같을 때만 근거가 된다.
- CI는 평가 SHA에서 수동 실행(`gh workflow run ci.yml --ref <그 SHA를 머리로 가진 브랜치>`)하거나, 그 SHA를 머리로 한 PR의 `gh pr checks`로 본다. 작업 줄기 push에는 CI가 돌지 않는다.
- 브라우저 실행은 맥 로컬 샌드박스 밖, 한 번에 하나, 시작·끝 1분 부하를 기록한다. 시작 부하 150 이상이면 그 실행은 무효다. 원문이 배율을 정하지 않은 시간 체크는 CPU 1배로 판정하고 4배 값을 기록한다.
- 무거운 실행(`bots36`, T5, `11-tech-balance`, `test-econ`)은 평가 SHA에서 한 번 돌린 결과를 여러 축이 인용한다.
- 독립 평가는 구현·이전 채점·자체 평가를 본 적 없는 새 세션 1명이 기본이다. 원문이 2명을 요구하면 2명, 둘이 다르면 낮은 쪽. 평가자에게 주는 입력 묶음을 체크에 적는다.
- 검사 기대값은 구현에서 베끼지 않는다. 출처는 명세(`docs/LEAGUE-CANON.md`, `docs/QUALITY-*.md`, `docs/DECISIONS.md`, 지시서)다.

## 4. 돌리는 법

1. 평가 SHA를 고정한다(고정본 워크트리, detached). 그 SHA의 코드는 판정 중 고치지 않는다.
2. `docs/qa/*.md`의 절차대로 체크를 판정하고, 결과를 **저장소 밖** JSON 파일에 적는다(점수가 드러나므로).
   ```json
   {"sha": "3f0d142", "date": "2026-11-01",
    "checks": {"UX-A-01": {"status": "통과", "evidence": "명령 · 로그 줄 · 캡처"}}}
   ```
3. `python3 tests/qa/score.py <결과 JSON> --open-severe <열린 blocker·major 수>` → 항목·축 점수, 개발 단계 점수, rc·정식판 판정을 표준출력으로 낸다. 종료 코드는 정식판 가능일 때만 0이다.
4. '통과' 판정은 맥락 없는 다른 평가자가 증거를 다시 보고 반박을 시도한다. 반박되면 실패로 고친다.

## 5. 고치는 법

체크를 바꾸려면 `tests/qa/checklist.json`을 고치고 `python3 tests/qa/render.py`로 문서를 다시 만든 뒤, 이슈 브랜치 PR로 올린다. PR에는 원문 기준표와 바뀐 체크를 대조한 독립 검토(blocker·major 0)가 필요하다. 원문과 다른 해석을 넣으면 D 번호를 남긴다. 기준을 낮추는 변경은 근거(로그·결정)를 PR 본문에 적는다.

## 6. 처음 판정 전 알려진 한계

- 체크 가운데 기존 검사에 단언이 없어 기록 줄을 더해야 하는 것이 있다(각 체크의 '이미 있는 검사' 칸이 '없음' 또는 '부분'). 그 검사가 저장소에 들어오기 전에는 확인 못 함이다.
- 원문 조건 가운데 관찰 가능한 체크로 바꾸지 못한 것은 축 문서 끝 '체크로 바꾸지 못한 원문 조건'에 있다.
- 실기기·교실 체크의 기록 양식(CM-DEVICE)은 `docs/CLASSROOM-CHECK-LEAGUE.md`에 맞춰 둔다. 리그 VoiceOver 절차는 아직 없다(제안 체크).
